# Écarts API à résoudre ou à respecter côté frontend

Ces écarts proviennent de la comparaison du cahier des charges `frontend.md` avec les contrôleurs, services et DTO du backend présent. Ils ne sont pas compensés par des données inventées dans l’interface.

| Écran / parcours | Donnée ou opération indisponible | Conséquence front | Endpoint ou décision suggérée |
|---|---|---|---|
| Recherche de voyages | `GET /voyages` fournit une vue disponible, mais pas de filtres de ville/date/nombre de passagers documentés. | Filtrer uniquement les voyages effectivement renvoyés ; ne pas promettre une recherche exhaustive par paramètres. | Ajouter des paramètres de recherche validés si les filtres doivent être exécutés serveur. |
| Places | Le plan renvoie capacité, places libres et occupées. Aucun verrou temporaire ni date d’expiration de réservation n’est exposé. | Rafraîchir la disponibilité et revalider à l’envoi ; risque de course entre choix et achat. | Ajouter une API atomique de réservation temporaire/libération avec expiration et identifiant de commande. |
| Réservation client | Le DTO accepte un passager, un siège et des champs CNI/téléphone ; pas de groupe multi-passagers, consentement, procuration, code promo ou code pack. | Le parcours doit rester mono-passager et ne doit pas afficher les fonctionnalités absentes comme actives. | Élargir le contrat de réservation après définition métier et migration de schéma. |
| Confirmation et paiement | Le statut Monetbil est consultable par référence et téléphone ; aucun endpoint front de reprise de commande par utilisateur/session n’est fourni. | La reprise après fermeture ou perte réseau n’est pas garantie par l’interface. | Fournir une route authentifiée de statut d’une commande appartenant au client, avec référence stable. |
| Billet | `TicketPublicView` fournit code, passager, téléphone masqué, villes, bus, départ, siège, montant, statut et QR signé. Plusieurs mentions exigées ne sont pas dans le DTO. | Imprimer les champs réellement reçus seulement. | Ajouter des champs facultatifs après validation métier : classe, catégorie, mode/référence de paiement, validité, assurance et consignes. |
| Profil voyageur | Pas de lecture/modification du profil client, ni suppression ou export des données observés. | La page profil/confidentialité ne peut pas être fonctionnelle avec l’API actuelle. | Définir les endpoints et règles de protection des données avant de bâtir ces actions. |
| Authentification | Pas de mot de passe oublié, changement de mot de passe, consentement d’inscription ni révocation de jeton exposés. | Afficher seulement les parcours supportés ; ne pas simuler de récupération de compte ou de contrôle de consentement serveur. | Ajouter les fonctions côté backend avec jetons de récupération à durée limitée et traçabilité. |
| Hôtesse / embarquement | Pas d’API manifeste de départ ou de scan/validation d’embarquement dans les contrôleurs observés. | Pas de vrai écran de scan ni compteur embarqués/attendus. | Endpoints de manifeste et validation idempotente du QR à concevoir. |
| Chauffeur / incidents | Pas d’API feuille de route, déclaration de retard/panne ou affectation tournée accessible dans le périmètre observé. | Pas de vue chauffeur opérationnelle. | Exposer route et création d’incident avec règles rôle et historisation. |
| Chef d’agence | Annulation existe, mais pas d’API de gratuité motivée, validation de clôture journalière ou remboursement. | Actions absentes et non simulées. | Ajouter workflow d’approbation/audit avant de les afficher. |
| Packs / fidélité / promotions | Pas d’API packs, compteur fidélité, billet offert ou vérification de code promotionnel dans le front controller/service observés. | Les contenus de ces sections peuvent être explicatifs, mais aucun solde/remise ne peut être calculé comme une donnée réelle. | Définir modèle, règles d’éligibilité et endpoints de consultation/application. |
| Bagages | Le modèle métier « un bagage inclus / excédent au kilo » n’est pas proposé par les API observées. | Ne pas calculer de supplément bagage côté navigateur. | Endpoint de devis/validation tarifaire si la vente de bagage est prioritaire. |
| Fret colis | Le front peut créer/lister/suivre/remettre les colis, mais aucun endpoint de devis des frais ou de SMS de code n’est exposé dans les contrôleurs. | Le calcul et la notification réels doivent rester serveur ; le frontend ne doit pas annoncer un SMS si l’API ne le confirme pas. | Ajouter devis de frais et statut de notification si le service les prend en charge. |
| Caisse | API d’ouverture, session active, relevés, paiements et fermeture disponibles. Pas de validation de clôture quotidienne par chef/comptable exposée. | Réaliser les opérations disponibles, laisser la validation journalière hors interface active. | Ajouter route de validation avec rôle, motif et journal d’audit. |
| GPS | Positions live et alertes disponibles ; pas d’endpoint historique utilisé par le front ni de flux temps réel STOMP documenté dans le contrôleur. | La carte peut afficher des positions reçues ; ne pas fabriquer de mises à jour « live » ou de retard. | Documenter le WebSocket existant ou ajouter pagination/historique et flux authentifié. |
| Administration | Endpoints de lecture référentiels, utilisateurs et profils, création utilisateur ; pas de mise à jour/suppression, tarifs, classes, promotions ou audit en lecture seule identifiés. | L’administration doit limiter ses actions aux lectures et créations présentes. | Ajouter routes métier explicites et droits côté serveur avant d’étendre l’UI. |

## Point de sécurité à auditer avec l’équipe backend

La configuration globale exige un JWT sauf quelques routes publiques ; les annotations `@PreAuthorize` sont présentes seulement sur une partie des opérations. Certaines lectures et pointages reposent donc principalement sur la règle globale authentifié, sans séparation métier visible dans les contrôleurs. Le frontend masquera les actions selon le rôle, mais cela ne remplace pas une autorisation côté serveur. Toute modification de sécurité backend dépasse le périmètre de refonte front et doit être traitée séparément.

## Vérifications complémentaires réalisées pendant la refonte

- **Paramètre opérateur Monetbil** : le DTO dit `MTN` ou `ORANGE`. Les anciennes valeurs front `CM_MTNMOBILEMONEY` et `CM_ORANGEMONEY` étaient incompatibles. Le front utilise désormais les valeurs du DTO. Un paiement réel reste conditionné par des identifiants Monetbil et un webhook public joignable et signé.
- **Double soumission et réservation** : le front bloque un second clic pendant une tentative. Le backend n’expose pas de clé d’idempotence. La création du billet et la demande Monetbil restent donc vulnérables à une répétition après coupure ou rechargement ; une protection serveur atomique est nécessaire.
- **Durée de réservation** : le dépôt de siège n’est pas une API dédiée. La requête de lecture de disponibilité traite les billets `EN_ATTENTE_PAIEMENT` récents comme occupés pendant une période distincte du délai RG06 demandé. Aucun compte à rebours ou libération explicite n’est retourné par le serveur.
- **Dates des départs** : l’API sérialise des heures locales sans fuseau. Le front interprète ces valeurs comme `Africa/Douala` (UTC+1), filtre les départs passés côté client et les trie par heure. Le filtrage serveur reste préférable.
- **Opérateur et payeur** : l’API Monetbil accepte un numéro indépendant du téléphone enregistré du passager ; la réservation exige le téléphone associé au compte. L’interface distingue ces deux champs.
- **Historique client** : `/billets/mes-billets` retourne actuellement seulement les billets `VALIDE` et `EMBARQUE`. Les états annulés, passés ou en attente ne peuvent pas former un historique client complet.
- **Billet** : la vue disponible n’inclut pas la référence de transaction Monetbil, la CNI masquée, la classe, la catégorie, la validité, l’assurance ou les consignes. Le billet imprimé utilise uniquement le nom, trajet, date, bus, siège, montant, code et QR signé disponibles.
- **Colis** : le backend stocke les frais fournis par l’agent et n’applique pas le calcul RG24. Le formulaire ne simule pas un devis ; le tarif confirmé par l’agence doit être saisi. La création n’a pas de retour de code SMS à afficher comme preuve d’envoi.
- **Rôles incomplets** : aucune route d’opération manifeste/embarquement pour hôtesse, feuille de route/incidents pour chauffeur, ni validation quotidienne de caisse n’a été trouvée dans le contrat consommé. Les écrans ne présentent pas ces opérations comme fonctionnelles.
- **Consentement** : aucun champ du DTO d’inscription n’enregistre le consentement à la politique de confidentialité ; il n’y a donc pas de case dont l’acceptation serait faussement présentée comme enregistrée.
